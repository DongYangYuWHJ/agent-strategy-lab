# 013：任务区分度与任务集校准

建立：2026-11-01；更新：2026-11-03。状态：候选任务通过离线审计，两模型 18 项首轮付费筛查已完成；尚未进行重复、Sol 对照或建立独立留出集。

## 实验发现

此前选用的算法题、原创仓库任务，以及新加入的 TinyDB／ItsDangerous 升级任务，在有效完成的运行中频繁出现多个模型全部通过。最近两项纯 Python 任务中，Luna 与 DeepSeek 均通过最终验收；这支持当前任务的质量区分度不足，不足以证明模型能力相同。两题各一次也不足以正式认定任务已经饱和。费用、耗时和用量数据仍有价值；额度、传输及环境异常不作为能力失败。

因此调查现代 benchmark 如何处理区分度不足：

- [Terminal-Bench 4.0](https://www.tbench.ai/news/terminal-bench-4-0)：校准环境资源、修复验收问题，并移除被多类模型反复完成的饱和题。
- [FeatureBench](https://arxiv.org/abs/2602.10975)：从真实仓库构造完整功能开发任务，通过执行测试验证新功能，同时保留其他功能。
- [SWE-CI](https://arxiv.org/abs/2603.03823)：通过连续需求迭代观察功能维护与回归，而非只评价一次静态修改。

这些方法为本项目提供设计依据，不意味着相关官方任务已经能在当前 Windows 环境直接运行。

## 本项目的具体措施

1. **保留旧数据，划分用途。** 现有高通过率任务保留为流程与成本基线；暂不继续用它们作为架构质量优势的主要证据。重复确认稳定全通过后，可移出主要能力比较集，但不删除历史结果。
2. **先扩充候选任务，再做模型校准。** 首批目标为跨至少三个真实纯 Python 项目的 6–10 项候选任务。优先选择跨模块功能、旧数据／API 兼容、状态与持久化一致性、多个接口协同行为；评价实际修改范围与约束关系，而非仓库总行数。固定源码、需求与来源；区分真实 issue 与人工构造合同。
3. **先把验收做扎实。** 每题明确需求对应的测试组，分别报告新功能完成情况与旧功能回归；同时保留全通过指标。加入起始版本失败、参考实现通过和典型错误实现失败的对照。隐藏测试只检查已声明需求，不加入未说明要求，也不反馈给 Agent 修题。
4. **保留真实工作中的测试与修复。** 沿用 OpenCode，允许 Agent 在一次运行内反复检查和修改。第一阶段保持现有四轮流程，避免同时更换任务和交互机制。后续另设连续需求任务：基于上轮产物加入新需求，并重新检查之前的功能。
5. **先比较单体，再比较架构。** 新候选先用 DeepSeek、Luna、Sol 单体进行初筛；对有代表性的任务，每模型独立运行三次，预先固定参数、工具、资源与整批预算。分别记录质量失败、资源停止和环境异常，不自动重跑或调参。三次只是初步稳定性检查，不据此宣称显著差异。
6. **冻结评估集，再验证架构收益。** 公开任务筛选规则及全部初筛结果，保留容易、部分完成和较难任务；允许建立明确标注的挑战子集，但不把它的结果当作总体工作能力。另留未参与调参的独立任务。只有确认存在质量或达到相同质量所需资源的差异后，才在冻结任务上比较单体与 Planner→Executor。

## 如何判断是否解决问题

目标是得到有有效验收、失败原因可解释、重复结果具有一定稳定性的任务分布。主报告同时呈现全通过率、按需求组的完成率、回归情况、费用与耗时；不将测试数量当作需求权重，也不将成功运行的平均费用当作包含失败成本的总收益。

如果更扎实的任务与独立评估中便宜模型仍稳定完成，就接受它在该任务分布上更具成本优势的结论，不以制造昂贵模型优势作为选题目标。
