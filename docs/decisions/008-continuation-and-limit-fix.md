# 008：提高输出额度，分开传输大小与 Token 预算

记录日期：2026-10-21。状态：已实现并通过离线验证；后续线上验证结果见文末补记。

## 背景与原因

用户同意采用 [007 的 16384 候选输出额度](007-output-token-budget-proposal.md)，同时修复 Luna 的运行问题。[004](004-output-budget-and-failure-types.md) 已确认两个独立问题：模型输出被截断后误触发提交；Luna 的加密推理续接内容使后续请求超过本地 32000 字节。

当前 OpenAI 适配器采用 `store: false`，每次发送完整对话，并通过 `reasoning.encrypted_content` 保留推理状态。这些字段是给接口续接使用的加密信息，不能理解为可读的推理文本，也不应为了缩小请求而随意删掉。上轮两道困难题重建的下一次请求约为 36832、37102 字节，因此被本地门槛拦截；这个失败不是供应商报告模型上下文已满。

推理输出额度用尽、加密状态进入请求、请求在本地被拦截是不同环节。旧框架还在二者之间错误地触发了公开验收与修复反馈，影响了最终停止原因。

## 本次实现

- `configs/models.json` 中 **DeepSeek Flash 和 Luna** 的 `max_output_tokens` 从 2048 提高到 **16384**；保留原推理档位。其他候选模型继续沿用原输出额度，不能把本次设置称为所有模型已经验证的默认值。
- 原生运行器默认与各真实实验配置的 `max_request_bytes` 改为 **1048576（1 MiB）**。这是传输包大小保护，不是模型上下文窗口，也不意味着需要用满这些空间。
- 新增 `max_estimated_input_tokens=64000`，独立限制本次输入的保守估计。整题累计 Token、金额、时间、调用次数等继续限制；本次没有提高这些额度。演示用的 mock 配置仍保留原传输额度。
- 对 OpenAI 请求做准入估计时，从临时估计副本中排除 reasoning 项的 `encrypted_content`，普通字段按序列化 UTF-8 字节加 2048 协议余量估计；再累加产生加密项的各次响应的**完整输出 Token 数**。完整输出包含可见内容，取此值而非只计 reasoning，是保守预留；可见字段也仍计算。实际发出的请求与落盘记录完整保留加密信息，没有解密、裁剪或启用服务端对话存储。
- DeepSeek／Anthropic 普通协议内容继续按字节加余量估计。传输超限为 `request_size_limit`，估计输入超限为 `input_estimate_limit`，避免把本地限制混写为模型上下文耗尽。请求准备阶段记录传输字节与估计输入，即使随后未发送也可追溯。
- OpenAI 的 `incomplete`、DeepSeek 的 `length`、Anthropic 的 `max_tokens` 在工具执行／提交之前识别。明确输出耗尽停止为 `output_token_limit`；DeepSeek 的 `length` 也可能表示上下文长度问题，因此仅当实际输出达到配置额度时归为输出耗尽，否则记录 `generation_length_limit`。其他已识别的未完成 OpenAI 响应为 `incomplete_model_response`。
- 截断响应的用量先记录；不执行部分工具调用、不触发提交验收、不占用修复次数、不自动发出额外付费重试。新的单次输出额度仍可能不够，此时会明确停止，供后续调参分析。

## 为什么 Token 与字节不能互相代替

输出上限约束这一次生成；传输上限约束下一次上传的 JSON 包。包里包括题面、历史、源码、工具定义、工具结果、协议字段和可能的加密续接信息。不同文字、编码和供应商协议都改变字节／Token 比例；密文尤其不能按普通自然语言换算。

两者有间接联系：允许更长输出，可能产生更多代码、工具参数或推理状态，后续请求也可能变大。提高输出上限不会自动提高传输上限；放宽传输门槛也不等于增加模型的生成能力。

该问题不限于 Luna。其他经同一 OpenAI 无状态适配器使用的推理模型也可能触发；DeepSeek、Claude 即使没有相同的加密字段，累积源码、工具反馈或思考内容后也可能碰到本地大小保护。统一分开限制，但不推断各供应商具有相同的状态协议或用量规则。

## 验证与证据

- 单元与运行器测试覆盖：200 KB 加密续接信息保持完整，经过后续工具调用并通过独立验收；它在传输保护内获准，不再被当成 200000 输入 Token。
- 另测普通文本增长仍受估计输入保护、超大传输仍被拦截、整题 Token／金额预算仍有效；三家输出截断均不执行工具、不验收、不修复、不重试，并保留用量。DeepSeek 长度原因同时覆盖达到／未达到配置输出额度两种情况。
- 将两家上轮困难题的四组保存响应交给新解析器离线检查，全部能在首次截断处识别为输出额度耗尽，不暴露工具调用。[离线检查记录](../../artifacts/limit-fix-20261021/historical-response-audit.json)。这只是重解析旧数据，没有改写旧报告，也没有生成新模型成绩。
- 全套离线测试 **97 项通过**，耗时 58.644 秒。覆盖既有评分完整性、任务导入、费用、报告与新续接／截断处理。
- **8 份实验配置**及单任务默认 limits 均通过离线加载校验，DeepSeek／Luna 的实际目录额度确认为 16384。[配置检查记录](../../artifacts/limit-fix-20261021/config-validation.json)。`git diff --check` 通过。

## 边界与后续实验

输入计数仍是保守的工程估计，不是供应商认证 tokenizer 或精确费用上界。实际用量和费用始终按响应中的 usage 及冻结价格表记录；新估计不修改账单数据。1 MiB 也不是无限空间，复杂会话仍可能达到任一限制。当前不自动摘要或裁剪续接历史。

新输出额度与框架均发生变化，应使用新的输出目录。需要严格测量额度的影响时，应在同一修复后框架下重跑必要的低额度对照，不能把旧版 2048 与新版 16384 的差异全部归因于 Token。16k 能否改善实际解题仍需联网实验；本次未运行模型、未消耗 API 额度。

官方协议依据：[OpenAI 加密推理续接说明](https://developers.openai.com/cookbook/examples/responses_api/reasoning_items)、[OpenAI 未完成输出说明](https://developers.openai.com/api/docs/guides/reasoning)、[DeepSeek finish_reason 说明](https://api-docs.deepseek.com/api/create-chat-completion/)、[Claude stop_reason 说明](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons)。

## 后续线上验证：任务集的部分有效性

将单次请求等待上限配置为 300 秒后，两种单 Agent 在 12 题调参集上各运行一次，24 项全部执行完：Luna 通过 11/12，DeepSeek 通过 10/12，所有调用的用量记录完整。两者的简单题、中等题全部通过；困难题暴露了解法错误、单次输出额度耗尽和累计 Token 预算准入拦截三种不同问题。[本轮报告](../../artifacts/lcb-dev-16k-300s-once-20261021-01/report.md)

这轮单 Agent 实验验证了任务集在可执行、可验收、区分部分失败原因方面的有效性，可以继续作为任务集检验更多候选模型。每模型每题仅运行一次，且部分失败受预算限制影响，目前不据此判断模型的稳定排名或任务集的全面代表性；保留评估集尚未用于候选模型测试。
