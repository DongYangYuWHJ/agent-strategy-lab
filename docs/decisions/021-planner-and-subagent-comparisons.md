# Plan 21 · Planner 对照、子会话与交互路由

记录日期 2026-11-13。当前处于设计阶段，实验和交互路由待验证。

## 1. Sol 实施和审查时，Planner 用 Luna 还是 Sol

Plan16 固定 Luna 实施、自查和修正时，Sol 规划组通过 11/12，Luna 规划组通过 8/12。待验证的问题是，实施、审查和修正都交给 Sol 后，更换 Planner 是否仍会影响最终通过数。[Plan16 Planner 对照](016-planned-self-tests-and-review.md#planner-模型对照2026-11-07)

| 组别 | 规划 | 实施 | 审查 | 修正 |
|---|---|---|---|---|
| Luna 规划 | Luna | Sol | Sol | Sol |
| Sol 规划 | Sol | Sol | Sol | Sol |

两组均在同一会话中按轮切换角色，使用相同的四轮提示、工具权限、自测和最终验收。优先沿用 Plan16 的四道题，两组每题重复次数相同。比较逐题通过数、规划费用和总费用，检验 Sol 规划在 Sol 接手后的收益。

## 2. Handoff 与 subagent 的对照

早期 subagent 实验中的父 Agent 还负责后续复核，后来 handoff 让 Planner 在规划后退出。两种流程的费用差同时包含职责变化。新对照固定每轮负责的模型和职责，比较同一角色在主会话接手与在子会话执行的效果。[早期子会话实验](011-planner-executor.md) · [同会话交接实验](012-planner-handoff-and-routing.md)

- **优先比较 Reviewer。** 固定 Sol 规划、Luna 实施和修正、Sol 审查。给两组 Reviewer 同一份待审代码、原始需求和测试证据，使用相同的只读权限。Handoff 组在原会话切换到 Reviewer，subagent 组在子会话里审查，再把意见交回 Luna。观察子会话的审查能否发现不同的缺陷，以及修正后实际通过了多少验收用例。
- **再比较 Planner 和 Executor 的交接。** 固定 Sol 规划、Luna 实施、自查和修正。一组由 Luna 接管原会话，另一组将计划和必要的任务信息交给 Luna 子会话。先在同一小组任务上试跑，测量两种方式的费用差。

两项都记录端到端的费用和耗时，计入父 Agent 为委派、传递上下文和回报发生的调用，同时保留最终验收结果。子会话收到的信息和父 Agent 的参与次数随运行记录保存，便于解释费用差。

## 3. 按用户意图做交互路由

交互 Router 读取当前请求和相关对话。用户想了解现状、解释原因或讨论方案时，交给 Planner 或更擅长分析的模型回答。用户明确要求实施时，交给 Executor 修改和验证。比如「这个迁移会影响谁」走分析，「按刚才说的方案改」则结合前文交给 Executor。

开放式对话里，用户可以用不同措辞表达同一意图，也可以在追问后才同意实施。优先采用能结合上下文判断意图的 Router。验证时看它能否在只问问题时保持只读，并在收到实施请求时带上已经确认的约束。这一设计关注用户当前想做什么。此前的任务 Router 根据任务难度选择编码架构。[Plan20 任务路由](020-structure-router-comparison.md)
