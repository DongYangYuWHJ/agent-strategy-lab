# 004：区分模型失败与额度、运行器限制

记录日期：2026-10-21，回顾性补记。状态：现象已确认；相关额度调整和截断处理修复尚未实施。

## 观察与证据

原六道 LiveCodeBench 任务中，DeepSeek Flash 与 Luna 都完成 4/6：简单题、中等题全部通过，困难题没有完成。两批的任务指纹、框架与运行限制一致，但供应商接口、价格与推理档位不同。

困难题的源码副本没有发生修改。原始响应显示，两家都触及单次 2048 输出 Token 上限，推理消耗了该次输出额度，尚未产出代码工具调用。

- DeepSeek 的截断空回复被框架当作提交，最终记录为 `no_progress`。
- Luna 的截断空回复也触发了提交检查；随后请求包含加密推理续接内容，重建的下一次请求分别为 36832、37102 字节，超过本地 32000 字节限制，记录为 `context_limit`。

两批费用和已完成结果仍是有效观测，但不能据此把困难题归为“模型已尝试完整解法后失败”。

## 决定与方法依据

后续参数实验应分别处理单次输出额度、整题累计 Token、本地请求字节数、时间和预算。需要将响应截断与正常提交、错误解法、工具失败和验收环境故障区分。

比寻找一个不变的最佳 Token 数更有用的目标，是记录预算变化时的成功率、成本、耗时和失败类型，观察各模型的预算响应特征。比较相同预算下的表现与分别合理调参后的表现，应明确采用哪一种条件。

## 记录时的实施边界

已增加参数说明并保存原始结果，没有替用户提高 `max_output_tokens`，也没有修复截断空回复被视为提交的运行器逻辑。当前请求字节数的程序上限为 64000，不能假定只扩大单次输出就解决全部限制。更改参数后应使用新批次，保留旧报告。
