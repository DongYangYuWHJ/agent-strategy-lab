# 007：用分档实验选择单次输出额度

记录日期：2026-10-21。状态：研究与参数建议；尚未修改模型配置，也没有运行付费实验。

## 背景与本地证据

当前候选模型的 `max_output_tokens` 均为 2048。原六题中，两家模型在困难题上都出现输出额度用尽、尚未写入解法的响应。这个证据说明当前额度会干扰能力评估，但不能确定提高到多少就能解题，也不能证明所有任务都需要更长输出。详见 [004：失败归因](004-output-budget-and-failure-types.md)。

这里讨论的是每次 API 调用的生成上限，不是整题累计额度；对当前推理接口，推理 Token 也会消耗该次生成额度。提高上限允许更多生成，不要求每次用满，也不等于主动强制延长推理。

## 资料及适用边界

- [OpenAI 推理模型指南](https://developers.openai.com/api/docs/guides/reasoning)：初次实验建议为推理与输出预留至少 25000 Token，再根据实际使用调整。额度耗尽可能发生在任何可见输出之前。这是避免截断的起始余量建议，不是所有模型、任务的成本最优值，也不能直接推广成 DeepSeek 的官方建议。
- [s1: Simple test-time scaling（2025，v3）](https://arxiv.org/abs/2501.19393v3)：在经过微调的模型和数学任务上，通过控制思考结束、追加继续思考信号等 budget forcing 方法，增加推理计算能够改善部分成绩。该方法包含主动干预，不能等同于只修改 API 的输出上限，也没有证明本项目的编码任务应采用某个固定数值。
- [Token-Budget-Aware LLM Reasoning（v6）](https://arxiv.org/abs/2412.18547v6)：研究通过预算提示和按题复杂度调整推理长度，以较小的性能损失降低 Token 成本。它支持按任务寻找效率平衡的思路，但其提示控制方法也不同于 API 的硬上限。

以上资料于记录日查阅。数值建议来自本地现象和实验成本取舍，不是文献已经验证的本项目最优参数。

## 建议的实验设计

| 每次调用上限 | 用途 |
|---|---|
| 8192 | 较低成本对照，观察相对 2048 的截断改善 |
| 16384 | 建议优先验证的候选设置 |
| 32768 | 较高余量对照，检查困难题是否仍受输出额度限制 |

先在调参集固定一组覆盖简单、中等、困难的任务，保持提示词、工具、推理档位、修复次数和任务版本一致，比较这些档位。保留原 2048 的历史结果，但涉及框架修复后的严格比较，应重跑必要的基线，不能把不同框架版本当成只有额度变化。

记录成功率、截断次数、实际推理与输出 Token、包含失败在内的费用、耗时和停止原因。对影响参数选择的临界或波动结果做必要重复；若两个档位成绩接近且截断都少，优先较便宜的配置，并保留样本量不足的说明。最终参数在完整 12 题调参集确认后冻结，再用于 6 题保留评估；不要在保留集上反复选额度。

同一 Token 上限并不代表跨模型相同的计算量、费用或推理程度。后续可以分别报告统一额度比较与各模型调参后的比较。

## 开始前仍需处理的限制

- 当前运行器会把没有工具调用的截断空回复当成提交，应先修复并单独记录截断，避免把额度失败误判为错误解法。
- 当前实验 `max_request_bytes=32000`，程序允许的最大值为 64000。Luna 旧实验的推理续接内容已经使下一次请求超过 32000 字节。输出额度提高后，必须验证请求大小与续接处理，不能保证改成 64000 就足够；这也不是供应商的模型上下文窗口。
- 当前每题 `max_total_tokens=100000`，另有时间、金额、调用次数限制。预留机制按本次请求和最大输出保守检查剩余额度；提高上限会改变调用是否获准，即使模型实际没有用满。
- 实验前应核对接口对所选模型的实际支持范围。程序目前只允许单次输出上限不超过 32768，这不构成供应商能力承诺。
- 为每个额度保存独立的模型目录快照并使用新输出目录，避免覆盖旧报告；当前尚未创建这些实验快照。
