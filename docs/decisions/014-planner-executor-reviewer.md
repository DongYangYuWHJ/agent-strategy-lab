## 轨迹发现、分析与结论

### 1. 计划本身可能包含错误判断

令牌迁移专项三份 Sol 计划均认为，验签成功后的解码失败不应作为继续尝试其他候选的理由。这遗漏了“签名配置相同，但编码格式不同”的合法迁移情况。三份交接实现都保留了这一退出路径，最终均为53/57，跨格式分组0/4。同题成功的 Luna 单体则捕获解码失败并继续候选，57/57。

**观察结论：** 错误规划与错误实现存在一致关系，支持“计划可能传播共同误判”的解释；尚未通过随机对照证明规划导致失败。Sol 单体同题也只有1/3通过，不能假设 Planner 总是正确。

### 2. 正确提醒没有自动转化为正确实现

缓存专项与组合的六份 Sol 计划都指出 TTL 链表复制风险，要求保留链接关系和元数据。部分 Luna 实现仍直接复制内部状态而未正确恢复链接，发生回滚失败。例如缓存组合第2次73/79，而成功的第1次实现补充了链接复制逻辑，79/79。其他失败实现还出现循环变量复用等代码问题，不能将所有失败归为同一个原因。

**观察结论：** 部分瓶颈位于实施与代码复核阶段。计划列出风险，不等于 Executor 已正确落实；增加规划信息也不必然补足实现能力。

### 3. 公开检查未暴露最终缺陷，自测能力存在边界

三组最后一次实施后的公开检查均为12/12通过；最终验收仍分别发现 Sol 3次、Luna 6次、交接7次未完整通过。交接运行在规划后各调用公开检查3至5次，重复相同场景不会增加这些检查的边界覆盖。这不代表没有进行代码复核，只说明已运行的公开检查没有暴露相应缺陷。

当前工具只允许执行预设公开检查、修改指定源码，未提供自行编写并运行针对性测试的能力。这个限制对三组相同，保留了组间公平性，但与日常开发不同；其对架构收益的影响尚未测量。最终隐藏验收能够检出缺陷，不应将开放隐藏反馈或降低评分要求作为修复手段。

### 4. 高价调用集中在事前，没有覆盖实现后的纠错

旧结构为 Sol 规划一次，随后 Luna 实施、需求复核和验证，Sol 不再介入。12次有效交接运行中，Sol 规划费用 $0.6441846，占有效运行费用 $0.869562380 的约74.1%；该比例排除旧中断，完整成本仍见上表。

**结构结论：** 当前配置使用了 Sol 的规划能力，没有使用它检查实际实现的能力。现有数据不支持这套交接配置带来稳定的质量与成本收益，也不足以否定所有协作架构。

以上为已有轨迹的观察分析，不是规划内容、模型能力、角色提示与工具限制的完整因果分离。诊断没有新增模型调用、重跑隐藏验收或改变旧结果。

## 新决定：Plan → Execute → Review

采用 **Sol Planner → Luna Executor → Sol Reviewer**。Reviewer 只审查，所有修改仍由 Executor 完成。

| 角色 | 模型 | 职责 | 权限边界 |
|---|---|---|---|
| Planner | Sol | 阅读原始要求与源码，提出方案、约束、风险和不确定性 | 只读；不实现、不改代码 |
| Executor | Luna | 实施、运行可用检查、交付；收到审查意见后负责修正 | 在原任务许可范围内写入源码；不能改验收器、配置或费用记录 |
| Reviewer | Sol | 对照原始要求、实际代码／变更和公开检查证据，指出缺陷与验证缺口 | 只读；不直接修改源码、测试或配置，不通过委派间接代改 |

拟保持同一会话按阶段切换 primary。Planner 与 Reviewer 是不同职责，即使使用同一模型，也必须分别计量。Reviewer 需要重新核对原始要求和实际实现，不能将先前计划当作正确答案；共享模型与历史不代表独立审查。

### 执行流程

1. **Plan — Sol：** 阅读并规划，明确关键约束和不确定性，结束本阶段。
2. **Execute — Luna：** 根据原始要求与计划实施，提供变更、公开检查结果及未验证部分。
3. **Review — Sol：** 审查当前实现，报告具体问题、对应要求、代码依据与可能影响；没有可确认问题时明确说明审查范围和剩余不确定性，不宣称外部验收已通过。
4. **Revise／交付 — Luna：** 有问题时核实并修正，运行可用检查，逐项报告处理情况；有理由不采纳的意见需说明依据。没有需要修改的问题时交付现有结果。
5. **最终验收 — 实验系统：** 对最终代码独立评分，不让 Reviewer 代替外部验收，不把隐藏结果回传用于本次修复。

首轮设计采用一次 Sol 审查和随后一次 Luna 修正／交付阶段；没有自动无限复审。各阶段内部仍可能包含多次 API 调用，不等于一次请求。是否增加复审及其停止上限，须在后续实现前另行冻结，不能失败后临时扩充。

Reviewer 的输出应是可操作的审查意见：位置或路径、违反的要求、证据、修复目标／验证建议，以及尚不能确认的风险。无需输出完整替换实现。即使 Reviewer 发现了明确修复方法，也由 Executor 执行修改。

只读职责同时由角色指令与运行器的工具权限落实，不能只依赖提示词中的“不要改代码”。该权限现已配置并通过本地验证，见实施补记。

## 要检验的假设与后续比较原则

**设计假设：** 让 Sol 审查已生成的代码，可能比只提供事前计划更容易发现具体缺陷；由 Luna 修正，可能在质量与费用之间形成更好的取舍。设计时没有新架构结果，不预设它一定更准确或省钱；首次正式结果见文末。

后续比较保留 Luna 单体、Sol 单体及旧交接结构作为参照，尤其不能只与昂贵的 Sol 单体比较。新增审查与修正的费用、调用、Token 和耗时全部计入，失败也计入；模型档位、任务、工具、预算和实际用户提示需在开跑前固定。历史批次单列，不能直接伪装成新架构的同期对照。

记录 Reviewer 找到了什么、意见是否有证据、Executor 是否落实、最终是否通过；这些过程指标用于解释结果，最终质量仍由外部验收判断。新流程同时改变了模型分配与复核方式，单次新旧差异不能直接归因于某一个因素。

本轮不同时开放新自测工具、加入 Router 或引入新模型。自测能力的扩展作为另一项实验变量保留；若以后实施，所有对照组使用相同能力，并单独冻结协议。不得把本轮隐藏失败点写进通用角色提示，再把原题改善当作独立泛化证据。现有四题可用于开发诊断，冻结方案后仍需独立任务评估。

## 实现与本地验证补记

新增策略 `planner_executor_reviewer`，`models` 按 **Planner、Executor、Reviewer** 排列。Sol可同时占第1和第3位置，但使用独立角色和权限。首轮沿用同会话切换，未改为子 Agent 委派，未增加自测工具或自动复审循环。

主要入口：

- [实验配置](../../configs/workflow-python-plan-execute-review.json)：Sol单体、Luna单体、旧Sol→Luna交接、新Sol→Luna→Sol审查四组，同四题、每格一次，共16项；整批 $5 上限。配置检查不产生费用；实现验证阶段未启动付费批次，后续正式结果见文末。
- [四轮工作流](../../configs/workflows/plan-execute-review.json)：`plan`只读、`implement`可写、`review`只读、`revise`可写。所有对照组使用同一组新提示与阶段写入限制；它与旧批次的四轮提示不同，不直接混合分母。
- [Executor指令](../../roles/workflow-review-executor.md)、[Reviewer指令](../../roles/workflow-reviewer.md)；Planner复用原规划指令，没有加入既有隐藏失败点。
- 调度与配置校验要求新策略严格符合四阶段顺序，错误配置在生成前拒绝。每次切换核对同一会话的角色与模型，三阶段模型可分别配置。

Reviewer工具列表不含写入，网关独立拒绝其写入及使用Executor端点；原生编辑、shell和委派同样被权限审计限制。每个只读阶段结束后还核对可编辑源码的哈希；越权改动停止运行。审查轮必须产生可见文本，空审查以 `missing_review` 停止，不继续修正或最终验收。

审查可见文本保存到每次运行的 `review.json`，原始逐轮消息及源码快照继续保留；不会提取 reasoning 内容。意见通过同一会话历史交给Executor，最后一轮由Executor核实、修改或保留并说明理由，之后系统统一验收。费用、Token和调用仍使用整段共享账本，事件和逐轮记录保留实际角色、模型与累计用量，不在交接时重置。

### Reviewer意见是否被落实

四项新架构记录中，三项审查后修改了代码，一项保留实现：

- **签名组合：** Reviewer指出同签名配置下跨格式解码失败提前退出，并提出实际验签signer时钟相关风险。Executor修改对应迁移路径，最终177/177。
- **迁移专项：** Reviewer指出跨格式回退遗漏，以及 `max_age=None` 时未来时间戳检查缺失，明确原规划不能替代任务合同。Executor加入对应分支，最终57/57；本批旧交接同题53/57。

### 回归的具体代码原因

在Luna规划组签名组合中，Reviewer提出自定义signer兼容性和时间戳换算风险，Executor随后修改了迁移路径。其中新增代码试图从 `signer.unsign(..., return_timestamp=True)` 返回的payload中，再用 `rsplit(...)[1]` 解析时间戳；但原 `unsign` 已经把时间戳移除，并另行返回datetime。该修改在正常timed场景触发 `IndexError`，新增24个原先通过的失败场景。

这明确定位了一处Executor修正实现错误。**不能据此直接认定Reviewer的建议是误报**：原实施在现有用例满分，不等于所有兼容性都正确；审查建议可能合理，但修复实现仍可能出错。没有执行“不给审查意见但保留修正轮”的反事实对照，因此也不能把所有前后变化都归为Reviewer的独立贡献。

Sol规划组缓存组合还有混合效应：修正消除了5个回滚失败，却新增TTL保留失败，净分数73→77但仍未通过。仅比较总分会漏掉新增回归，逐场景编号比较能将两者分开。

### 更新后的理解与候选方向

当前流程的薄弱环节不仅是计划或审查能否指出问题，还包括**修正能否正确落实，以及新增回归是否可被执行阶段发现**。固定公开检查在这些场景中仍然通过，无法为Agent提供相应回归信号。下一步值得单独评估隔离的针对性自测与回归检查能力，所有对照组应同时获得相同工具，外部隐藏验收继续不可见；本次尚未实现该能力或启动新实验。

原始付费结果和费用结论保持原样，本次仅补充阶段归因，不挑选中间最好版本来替换最终交付。分数变化只说明代码修改的效果，不足以证明某Planner稳定优胜、Reviewer总能兜底或新自测方案有效。事后分析已知最终成绩，不是独立留出评估。
